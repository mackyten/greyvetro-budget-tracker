| TASK-002 | TASK-001 shipped per-user auth via direct Firebase Auth (Google Sign-In) instead of the `greyvetro-auth-hub` bridge, deliberately, to unblock real per-user Firestore rules without depending on Keycloak infra that isn't deployed anywhere reachable yet (`greyvetro-auth-hub`'s `docker-compose.yml` is local-only and wasn't running). The interim implementation was designed so this swap stays contained: `AuthService` (`lib/core/auth/auth_service.dart`) is a provider-agnostic interface with one implementation, `FirebaseGoogleAuthService` (`lib/core/auth/firebase_google_auth_service.dart`); everything downstream (Firestore rules, `FirestoreBudgetRepository`'s `users/{uid}/...` paths) is keyed on the resulting Firebase `uid`, not on how the user got there. | A backend (or Cloud Function) endpoint accepts a Keycloak access token from `greyvetro-auth-hub`, verifies its signature/issuer/audience against the `greyvetro` realm, and returns a Firebase custom token for that user's `sub` claim (`admin.auth().createCustomToken(uid)`), keeping `uid` stable across the swap so existing `users/{uid}/...` data isn't orphaned.<br>A new `AuthService` implementation (e.g. `KeycloakBridgeAuthService`) runs the OIDC flow against auth-hub, POSTs the resulting access token to that endpoint, and calls `FirebaseAuth.instance.signInWithCustomToken` with the returned custom token.<br>`main.dart` is switched to construct the new `AuthService` instead of `FirebaseGoogleAuthService` — `AuthGate`, `firestore.rules`, and `FirestoreBudgetRepository` require no changes.<br>`google_sign_in`/direct-Google sign-in is removed once the swap is confirmed working end-to-end.<br>A signed-out client still gets a permission-denied error from Firestore, verified against the Firebase emulator or a real deploy. | Hard |
